## Lessons from professional tools and researchers

These are design inferences from primary sources, not interviews about what all NASA engineers want.

- **IBM Quantum:** its jobs interface supports identifying, filtering, retrieving and saving job records/results. This motivates addressable analyses and reopenable JSON records; it does not justify adding quantum computation to a combustion tool, or prove that every external environment/input is archived. [IBM jobs documentation](https://quantum.cloud.ibm.com/docs/en/ibm-quantum-compute/save-jobs).
- **ParaView:** saved state captures pipeline/view configuration; loading may require resolving source-file locations. A state file alone is not the data. IGNIS therefore preserves recipes separately from historical originals and includes the raw CSV in an explicitly exported local-data package. [ParaView saving results](https://docs.paraview.org/en/latest/UsersGuide/savingResults.html).
- **NASA combustion workflow:** the Liao task report describes experiment-specific optical thresholds, extraction of flow information from imagery and incomplete recovery. It also discusses model discrepancies. A future tracker needs declared calibration, timing, threshold sensitivity and failed-record retention. The report has a pressure-unit inconsistency between passages, so this review does not turn it into a new numerical combustion claim. [NASA TaskBook](https://taskbook.nasaprs.com/tbp/index.cfm?action=public_query_taskbook_content&TASKID=31FF2895CF11A3D63C9B8986DB12A22A).
- **Historical SpaceX engineering:** the SpaceX-authored 2011 Dragon air-circulation paper compares CFD with flight-like geometry/probe measurements. Fan flow was conditioned on measured flow and selected measurement locations considered CFD stability. Its useful lesson is geometry/operator/location alignment, not blind predictive validation. This is historical cargo-Dragon work, not evidence of current SpaceX internal fire tools. [NASA record and paper](https://ntrs.nasa.gov/citations/20110014250).
- **NIST:** FACT separates material-property calibration and verification work from experimental validation; NIST's material-characterization program links measurement scales and model needs. This motivates explicit observation/solver/hypothetical roles and a clear separation between fitted inputs and assessment data. [FACT](https://www.nist.gov/programs-projects/automated-tools-material-property-calibration), [material characterization](https://www.nist.gov/programs-projects/material-flammability-characterization).
- **MaCFP and FSRI:** shared formats, data quality, interlaboratory variability and accessible material-property/fire-test data are documented needs. They support building traceable data tools; they do not establish a universal demand for IGNIS or validate microgravity transfer. [MaCFP material database](https://github.com/MaCFP/matl-db), [FSRI material database](https://materials.fsri.org/), [FSRI data repository](https://github.com/ulfsri/fsri_materials_database).

## What is implemented

### Local data workbench

`/#local-data` accepts bounded UTF-8 CSV in browser memory: 1 MiB, 5,000 data records, 32 columns, four channels and at most 128 run/phase groups. A user selects delimiter, header/data record boundaries, clock, units, run/phase identity, measurement operator, context and observation/solver/hypothetical origin. Unknown metadata must be stated explicitly. There is no automatic unit conversion, clock alignment or cross-file join.

Raw bytes, BOM and line endings are preserved. Malformed quoting/structure is rejected; unavailable/invalid numeric cells remain in the ledger. User-declared sentinel strings are matched exactly; zero and `-9999` are never presumed missing. Decimal parsing is strict and values use JavaScript binary64; decimal rounding and repeated represented times are disclosed. No imputation, sorting, resampling, smoothing or independent-sample assertion is performed.

The researcher selects one run/phase and an inclusive time window, inspects disconnected observations and raw records, and receives descriptive extrema/counts with source-row witnesses. Missing values remain visible. Export explicitly includes raw text, filename, declarations, recipe, result and checksums. Replay re-parses the raw file, checks method version and recomputes the result; it does not trust a stored answer, even if its checksum was recomputed. Checksums establish internal consistency, not authorship or instrument accuracy. The local CLI uses the same engine and refuses to overwrite an output file.

The committed five-record [CSV](../artifacts/workbench/hypothetical.csv), [mapping](../artifacts/workbench/hypothetical-mapping.json) and [package](../artifacts/workbench/hypothetical-package.json) are **hypothetical**, not extracted paper measurements. The UI's illustrative example is separately labelled hypothetical. No private researcher data were used or sent to a provider.

### SI: Scientific Intelligence

`/#si` provides a question, explicit scope fields, review/confirmation, source-linked assessment, notebook recording and Markdown/JSON export. Structured mode is identified accurately: it does not call a language model. The question is preserved verbatim; choices, catalogue revision and attached selections bind the review/result. Editing or changing evidence context invalidates pending results. Failed requests can be retried only against the current request. There is no chat history or BYOD auto-attachment.

`GET /api/si` describes preparation status for **Groq GPT-OSS 120B** and **Gemini 3.8 Flash** only. `POST /api/si` previews the exact instructions, public catalogue definitions and closed schema with the user's question/explicit IDs. Extra fields, unknown/duplicate IDs and stale configuration/catalogue bindings are rejected. It **does not call a provider**. The preview is not a claim that arbitrary user text is approved for the existing research evaluation.

The existing direct adapters and frozen `GROQ-OSS120-LOW` / `GEM38-LOW` candidates remain. Groq 120B is the provisional first candidate because strict schema support and the current $0.15/$0.60 input/output per million rates fit this constrained interpretation task. This is a cost/compatibility choice, not measured task superiority; an earlier contract failed evaluation. Both Groq OSS sizes currently support strict outputs; streaming/tool use are not part of that mode. [Groq models](https://console.groq.com/docs/models), [structured outputs](https://console.groq.com/docs/structured-outputs).

Gemini 3.8 Flash is the existing second candidate, with frozen $0.75/$3.75 input/output rates per million. Current pricing states those standard rates through 31 December 2026, with changes afterward; provider terms distinguish free and paid data use. No newer Gemini model was silently substituted. [Google pricing](https://aistudio.google.com/docs/pricing).

**Live interpretation, new semantic error rates, schema-failure rates, provider latency and billed usage: NOT RUN.** No credential was inspected, account funded or acceptance gate changed. Existing evaluation splits, call/probe limits and cumulative conservative accounting remain authoritative; keys alone do not enable runtime. Legacy `AI_*`, `aiAvailable` and stored schema fields are retained for compatibility; user-facing runtime terminology is SI. The AI development-disclosure label remains accurate.
